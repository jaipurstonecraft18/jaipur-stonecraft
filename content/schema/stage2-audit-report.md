# Jaipur Stonecraft — Existing Data Audit Report (Stage 2)

## Audit Objective
Per Section 41 of `PRODUCT-ARCHITECTURE.md`, this report documents the complete audit of existing content files (`collections.js`, `categories.js`, `designs.js`, `products.js`, `marble.js`, `projects.js`) prior to Stage 3 migration.

---

## 1. Key Inconsistencies & Data Issues Identified

### Issue 1.1: Product Alias Confusion in `content/products.js`
- `content/products.js` currently re-exports `categoriesData` (`export const productsData = categoriesData;`).
- **Impact**: Category nodes (such as `ganesh-ji`) are treated interchangeably with specific Product Artworks (such as `seated-ganesh-with-modak`).
- **Migration Remedy**: Stage 3 will decouple Categories from Product Artwork entities in the database API layer.

### Issue 1.2: Placeholder Text & Image Assets in `content/designs.js`
- `content/designs.js` dynamically generates 386 design entries across 96 categories.
- **Text Gap**: All 386 designs use generic placeholder text:  
  `"[DETAILED DESCRIPTION PLACEHOLDER: Hand-carved ... from solid stone block. Detailed masonic chiseling and finishing according to client specification.]"`
- **Image Gap**: All 386 designs use `https://placehold.co/800x600/...` placeholder URLs without WebP / AVIF fallbacks or responsive metadata.
- **Migration Remedy**: Stage 3 will populate rich masonic descriptions and real image metadata structures.

### Issue 1.3: Flat Generic Material Strings
- `designs.js` assigns identical generic string arrays for `variants.materials`:  
  `["White Makrana Marble", "Pink Bansi Sandstone", "Black Marble", "Beige Limestone"]` across all products.
- **Impact**: A white marble statue page lists sandstone as a variant without material origin metadata or durability guidance.
- **Migration Remedy**: Connect all products to the central `materialsDB` defined in Stage 1 & 2.
